# Versioning and Package-Lineage Plan

Recode diverged from its Pi integration source while custom package versions were bumped independently of a clean standalone release line. Before public npm publication, establish a new coherent Recode version lineage without pretending that existing registry versions can be replaced or rewritten.

This plan is repository policy work. It does not authorize npm queries, package publication, Git tags, remote creation, or release mutation.

## Approved direction and unresolved value

Use new `@reitaard/recode-*` identities and a **synchronized fixed-version release train** for all public Recode packages initially. The first release uses the Creator-approved custom bootstrap version, independent from Pi/RePi numbering. `0.84.0-beta.1` is already deprecated and must not be reused, suggested, or treated as the bootstrap.

The Creator selected `0.1.0` as the fresh standalone bootstrap. It is a normal release version, not an alpha/beta continuation and not evidence of completed publication certification.

Every package participating in one public release receives the same version, including packages whose source did not change. Internal dependencies use the same compatible version range generated by the release tooling.

Why start fixed-versioned:

- the packages are tightly integrated and currently released/tested together;
- users can report one Recode version across CLI, Agent, AI, TUI, telemetry, storage, and Maestro;
- compatibility is easier to understand during the public reset;
- release manifests and binary provenance have one product version;
- it avoids accidental combinations of independently bumped packages before compatibility policy is mature.

Independent package versioning can be reconsidered after stable public APIs, package ownership, compatibility tests, and several successful releases exist.

The selected standalone identities are:

| Package | Intended role | Initial release-set decision |

| `@reitaard/recode-telemetry` | generic telemetry contracts | public runtime package |
| `@reitaard/recode-ai` | model/provider APIs | public runtime package |
| `@reitaard/recode-agent-core` | Agent and AgentHarness | public runtime package |

Do not publish a mixture of `repi-*` and `recode-*` identities accidentally. Old names remain historical predecessors or verified compatibility identifiers only; no compatibility publication is implied. The `@reitaard` scope must be controlled by the Creator's npm organization/account.

## Registry facts required

npm versions are immutable in practical release planning: an already published `name@version` cannot be replaced with different contents. Unpublishing does not make version reuse a safe policy and may be restricted by npm.

Before applying the custom bootstrap version, record for every intended package:

- whether the package name exists;
- package owner/maintainer accounts;
- latest published version and dist-tags;
- all previously published Recode-derived versions;
- whether provenance/trusted publishing is configured;
- whether the package is public or private;
- whether any name is owned by someone else;
- whether the current migration-source contents have ever been published under that identity and version.

Capture only public registry metadata. Never store npm tokens, recovery details, private organization data, or credentials in this repository.

No registry inspection should occur until the Creator approves that network action.

## Custom bootstrap version

Do not choose the version by comparing with upstream Pi/RePi or by incrementing the deprecated `0.84` line. Upstream versions describe integration provenance, not Recode's release lineage.

The Creator-approved `0.1.0` is the single source value for the initial fixed train. Then:

1. verify that exact version is unused for all seven new package names;
2. record its intended maturity/channel and ensure it obeys SemVer/npm syntax;
3. synchronize manifests, lockfiles, internal ranges, CLI metadata, release manifests, binaries, changelogs, and Git tag expectations;
4. fail if any inherited `0.83.x`, `0.84.x`, or independently bumped package value leaks into release output.

Do not insert a guessed concrete version. Registry inspection verifies availability; it does not choose or replace the custom bootstrap value.

## Upstream lineage

Track upstream integration separately from SemVer.

Each Recode release manifest should record:

- Recode product version;
- source Git commit and clean-tree state;
- integrated upstream Pi version/tag/commit, when applicable;
- Recode baseline/merge-base or port provenance;
- package versions and artifact hashes.

Do not encode the upstream version into the normal package version or keep bumping Recode solely to match upstream. A Recode release may integrate several upstream versions, skip versions, or contain no upstream change.

## SemVer policy

While the product remains below `1.0.0`:

- patch: compatible fixes, docs, tests, and internal changes without intentional public contract expansion;
- minor: new public functionality or an intentional breaking change that is clearly documented during `0.x` development;
- prerelease: public validation that must not receive the `latest` dist-tag;
- stable `1.0.0`: only after the public API/support/compatibility policy is mature enough to make normal SemVer major-version promises.

Even though SemVer permits broad breaking changes during `0.x`, Recode should document migrations and avoid gratuitous breakage.

## Dist-tags

Use explicit channels:

| Release | npm dist-tag |
|---|---|
| alpha | `alpha` |
| beta | `beta` |
| release candidate | `next` |
| approved stable | `latest` |

Never assign `latest` during migration testing. Moving a dist-tag is a remote mutation and requires explicit release authorization.

## Git tags and changelogs

Use one product tag per synchronized release:

```text
v<recode-version>
```

The tag must point to the exact certified source used for packages and artifacts. Do not recreate, move, or force an existing public tag.

Package changelogs may remain package-local, but one root release note should summarize the product release and link package-specific breaking changes. Changelogs are provenance; they must not claim unsupported recovery, platform, or publication behavior.

## Internal dependency policy

Release tooling must derive internal package ranges from one approved package graph rather than maintaining conflicting lists.

For synchronized `0.x` packages, choose and test one generated range policy rather than embedding an example release number in documentation. A caret range on `0.x` does not cross the next minor version, which limits accidental compatibility. Prerelease packages require exact or deliberately tested prerelease ranges because ordinary SemVer range behavior can exclude prereleases unexpectedly.

Workspace development may use workspace protocol/ranges only if npm packaging rewrites them deterministically and tarball inspection proves the published manifests are correct.

## One package graph

Replace the current conflicting package sets with explicit generated constants or one declarative release configuration:

- workspace/build packages;
- public npm packages;
- binary-embedded packages/assets;
- workspace-only/test packages;
- optional packages such as SQLite.

Every release script consumes that owner or derives a reviewed subset from it. Tests must fail when a publishable internal dependency is absent, versions diverge, dependency ranges disagree, or an unapproved workspace enters a tarball.

## First standalone build synchronization

The first post-transfer build starts from clean approved source inputs. It must not reuse inherited build output or carry the migration source's custom version forward implicitly.

Before invoking the root build, synchronize these connected files and generated contracts in one reviewed change:

- root `package.json` and every public/workspace package manifest;
- all internal dependency and peer-dependency ranges;
- root lockfile and the coding-agent publication shrinkwrap;
- install-lock only if it remains approved;
- CLI/product version constants and package metadata;
- release identity policy, release-package graph, and version-sync script;
- release manifest, artifact-index, binary, Termux, and local-install metadata inputs;
- changelog/release-note headings and tag expectations;
- tests/fixtures that intentionally assert release identity.

Then delete/refuse inherited `dist/`, binaries, archives, tarballs, declarations/maps, caches, and temporary release output; run a deterministic no-refresh build; inspect generated changes; and proceed to tests and package-content checks. The permanent operator procedure is recorded in [Build and Install](../../setup/BUILD.md).

## Release sequence

1. Record the approved `@reitaard/recode-*` package map and public package set.
2. Use the recorded bootstrap version `0.1.0`.
3. Inspect public npm metadata and verify that the new names and exact bootstrap versions are available.
4. Rewrite standalone release identity and package graph.
5. Synchronize manifests and lockfile deterministically.
6. Build and run credential-free tests.
7. Compile retained examples and protocol/schema drift checks.
8. Inspect every `npm pack --dry-run` result and unpacked tarball.
9. Test installation from local tarballs in an isolated directory.
10. Build and verify binaries separately.
11. Publish prereleases only after explicit Creator approval.
12. Verify registry package contents, provenance, dependencies, and dist-tags after publication.
13. Promote to stable only through a separately approved release.

## Failure and recovery

- Never reuse or overwrite a published version.
- If one package publishes and another fails, stop; do not silently move `latest` or claim a complete product release.
- Record the partial state and publish a new synchronized version after correction. Do not attempt to make different contents share the failed version.
- GitHub Release and npm publication are separate remote transactions; release policy must define which becomes visible first and how partial state is communicated.
- A failed prerelease may remain visible as provenance. Deprecation is preferable to pretending it never existed.

## Files that eventually own the policy

During migration this plan belongs under `docs/migration/plans/`. Before public launch:

- stable SemVer, compatibility, package-set, and dist-tag policy moves to permanent release documentation;
- current registry inventory and reset notes may remain migration-only and be deleted after handoff;
- release scripts/tests become mechanical authority for synchronization;
- public release notes explain user-visible changes, not migration history.

Do **not** place this entire plan in `.gitignore`. Versioning and release policy must be reviewable and version-controlled. Only credential-bearing or account-private notes must stay outside Git. A temporary public-registry inventory may be tracked here because npm package metadata is public, but it should contain no secrets and can be removed with other migration material after the clean lineage is established.

## Decisions requiring Creator approval

1. Bootstrap version `0.1.0` is approved.
2. SQLite is approved in the initial seven-package public train at `0.1.0`.
3. Choose dist-tag policy and stable-launch threshold.
4. Choose DCO/CLA contribution policy and how external changes affect changelogs/releases.
5. Approve all npm queries, trusted-publishing setup, publication, tags, and remote release actions.

The new `@reitaard/recode-*` identities and synchronized fixed train are selected directions; changing either requires an explicit new decision.
